Case study: event bus$ git show e7e47b5 -- docs/event-bus.md

How I introduced event-driven integration at getolo. I've generalised internal service, repository and event names, and left out colleagues and partners. The design and the decisions are as built.

The problem

The core app (Rails, Postgres) owns leads and customers. Marketing, sales and data needed to react to changes there: send conversions to ad platforms, notify partners, feed the warehouse. Each need became another webhook or Zapier flow coupled to the core app, fragile and hard to debug.

The goal was for the core app to publish domain events reliably, and for other teams to consume them without learning delivery semantics or touching the core app.

Contract and constraints

Delivery is at-least-once. A message can arrive more than once, so every consumer deduplicates on event_id.

Consumers aren't isolated from each other in AWS. They share one task role, so the access policy is one explicit shared policy, not per-consumer policies that would only look like isolation. Real isolation would mean separate tasks, and that's a future decision.

Configuration is explicit. Each consumer sets its own visibility timeout, retention and maximum receives, and the shared module has no hidden defaults.

Why this design

  • No dual write. The event row commits in the same transaction as the domain change. Either both happen or neither does.
  • A relay that scales out. FOR UPDATE SKIP LOCKED lets several relay processes share the outbox table without stepping on each other. Failed rows stay put and are retried.
  • Managed services, no broker to run. EventBridge routes by event name and SQS buffers per consumer, both managed by AWS, where the platform already runs. I had a different opinion at first and came around.
  • Names that can't drift. Event names are derived from event classes (e.g. <app>.leads.created), never typed by hand.
  • A framework/plugin split. The runtime owns polling, acks, retries and dead-lettering. A team declares a queue, the events it wants, and a handle() function.

Where it stands

Verified
End to end on staging, including a hands-on workshop where non-engineers deployed their own consumers.
Live
Production infrastructure, since September 2026.
In progress
The first production consumer, which sends conversion events to ad platforms. Its agreed success measures are the platforms' event-quality scores and parameter counts.
Failure handling
  • Handler succeeds → the message is deleted. Handler raises → the message stays on the queue, is retried, and after the maximum number of receives moves to a dead-letter queue.
  • If a publish succeeds but deleting the outbox row fails, the relay publishes that row again on its next pass. That window is one reason the contract is at-least-once rather than exactly-once.
  • Dead-lettered messages are inspected manually. The runtime never reads from a dead-letter queue, so the access policy doesn't cover them.
  • Running several consumer tasks is safe because consumers share no state. Even at one task, rolling deploys briefly run two, so deduplication was never optional. I checked the runtime and the deploy config before answering that, rather than relying on intuition.
Governance and change
  • New event types need an engineer's approval, and new infrastructure needs the platform team's. Self-service doesn't mean ungoverned.
  • Changing an event's payload is an engineering change in the core app. A consumer team requests it; it doesn't make it.
  • A platform reviewer spotted that event names were interpolated into generated Terraform. I replaced that with an allow-list validated against the real event classes, which closes the injection path and catches typos.
  • Environment prefixes on queue names are added by the runtime. I argued for an explicit helper; we kept the implicit version for consistency, and I documented the reasoning.
Lessons
  • Read the code before answering a scaling question. The answer was in the runtime and the deploy config, not the architecture diagram.
  • Make the real boundary explicit. A policy that implies isolation you don't have is worse than an honest one.
  • Dogfood your own docs. Running the onboarding commands myself found three real bugs before anyone else hit them.
  • Not every environment deserves migration hygiene. I added state-preserving Terraform moved blocks to a disposable staging setup, then deleted them.

Projects$ ls ~/src

Things I built in public, and why.

guruji agent skill · markdown

What: an agent skill that turns a coding agent into a software-architecture mentor. It's plain markdown instructions, frameworks and templates, tool-agnostic, and originally built for Zed's agent skills.

Why: I wanted to get better at making and defending architecture decisions, and to keep an honest record of my real decisions, mistakes and wins instead of reconstructing them at review time.

Interesting decisions: "rigor never adapts, explanation depth does": the full trade-off framework runs every time, and only the explaining changes. It asks questions before answering. Safety policies (confirming destructive operations, flagging PII) are chosen by the user, and every confirmation is single-use.

mspm Go · BSD-3

What: multi-string pattern matching. Give it a list of keywords and a document, and it counts every keyword in one pass, using a trie inspired by Aho–Corasick.

Why: it came out of building an information-retrieval system at Codyssey, where matching many terms against many documents had to be fast.

Interesting decisions: two trie node implementations, a plain TrieNode and a map-backed TrieHashNode, benchmarked side by side. Search came out the same, and the hash node inserted about 40% faster.

RecommenderSystem Python · pandas · MongoDB

What: my 2014 thesis, a movie recommender. You rate 20 movies in a web UI, it clusters you with similar users (K-means), and it recommends from the five users closest to you.

Interesting decisions: a later version removed the collaborative-filtering stage and kept clustering alone. Shipping the simpler thing that works was a lesson I'd relearn many times.

Postmortems$ ls postmortems/

Blameless format, including when the person to blame was me. Each one changed how I work.

INC-001 The Friday deploy
What happened
A Friday release introduced duplicate webhook deliveries, and thousands of jobs piled up in the dead-job queue.
Response
I coordinated the incident, shipped a hotfix in about 90 minutes, and wrote a blameless postmortem.
Prevention
An anomaly monitor for the duplicate pattern, and a CI/CD guard against Friday deploys for the whole team.
Lesson
"Be more careful" isn't a fix. A rule the pipeline enforces is.
INC-002 Four workers, allegedly
What happened
The config said 4 Puma workers. The servers had quietly been running 3, because a "smart" restart never re-read boot-time config.
Lesson
Check the running process, not the file. Config is a wish; the process is the truth.
INC-003 Falling for my first theory
What happened
On more than one investigation I was sure I'd found the cause, then had to drop the theory when the data disagreed. Twice in one case.
Lesson
Write the hypothesis down, then try to prove it wrong before you tell anyone it's right.
INC-004 Too quiet in the room
What happened
Early on I'd have the right idea and not push for it. A colleague's feedback, in three words: "be more brave."
Fix
I started writing RFCs and leading the discussions, pushing back on vague answers, and holding a position under pressure while conceding the points that were fair.
INC-005 PR description: "see ticket"
What happened
My early pull requests were a ticket link and a prayer.
Fix
Now they carry context, a rollout plan, and a rollback plan that actually runs. Reviewers are noticeably less sad.
INC-006 Rust for everything
What happened
I started a computer-vision side project in Rust because it sounded fun, then found that the ecosystem I needed lived in Python.
Lesson
Choose the tool for where the problem lives, not for the vibe. (I still love Rust.)
INC-007 The 2× that wasn't
What happened
I estimated a search-latency fix would make it about 2× faster. Measured result: 15–25%.
Fix
I said so out loud, kept digging, and found the real bottleneck. The answer was to remove expensive work, not buy bigger machines.
Lesson
Estimates are hypotheses too. Measure, then report what you got.
